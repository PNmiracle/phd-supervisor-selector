# 改造验收 runbook

> **为什么需要这一份**：2026-10-07 的技能改造交付的是「让规则可被执行」的机制，
> **没有验证「规则是否真被遵守」**。静态检查只能告诉你规则在哪。下面三条是唯一能验证的办法。
> 其中 ①② 已尽可能脚本化，③ 只能真跑任务。

## 一条命令先跑完机械部分

```bash
python3 scripts/audit-all.py <DATASHEET_ID> \
    --main-table-id <学校主表 datasheetId> \
    --expected-programs expected_programs.txt \
    --evidence-top 5 --json data/audit-last.json
```

- **第 4 项 links** = 下面「验收② 链接抽检」的机械化版本（落点 + 是否本人页）
- **第 11 项 evidence** = 下面「验收① 证据链抽检」的机械化版本
- 退出码：`0` 通过 / `1` 有 FAIL / `2` 用法错 / **`3` 结果不完整**（不得算通过）

**⚠️ 脚本只给候选清单，不下结论。** `WARN` ≠ 通过；反爬 / SPA 壳导致抓不到正文的记录会被标注「无法机械判定」而不是误报——那些必须人工打开看。

---

## 验收① 证据链抽检（抽 3–5 条）

**问题**：这条备注里写的研究方向，出自哪个网址的哪句原文？

**机械部分**：`audit-all.py --only evidence --evidence-top 5` 会从 `备注` 与 `导师研究领域` 抽事实短语，用中文 4-gram 覆盖率（≥50%）与英文整词命中，对照三个链接的正文，输出「找不到出处」的清单。

- `导师研究领域` 在**健康的**首页上找不到出处 → **FAIL**（方向必须来自本人打开的官网原文）
- `备注` 里的事实短语找不到出处 → **WARN**（可能是同义改写，也可能是照抄了别处的摘要）

**人工部分（不可省）**：对清单里每一条，**打开原页读到那句话**，然后判定：

| 判定 | 处置 |
|---|---|
| 原文确实有、只是被改写 | 保留，把页面原句记进验收记录，作为对照改进 4-gram 阈值的依据 |
| 原文没有，但方向判断本身正确 | 改写成**页面原文的措辞**，或补上承载该说法的页面链接 |
| 原文没有、方向判断也站不住 | 删除该条记录，并回溯：这条是怎么进候选池的？要不要补一条硬门？ |

**通过标准**：抽检的 3–5 条里，凡被判 FAIL 的都已处置；WARN 每条都有明确结论（保留并记原句 / 改写 / 删除）。

## 验收② 链接抽检（抽 3–5 个链接）

**问题**：这个链接最终停在哪个网址？页面正文里有没有这位导师的名字？

**机械部分**：`audit-all.py --only links` 已经在报这两件事——`curl -L -w "%{url_effective}"` 的最终落点，与正文是否含导师姓氏。

**人工部分**：对 `403 / SPA 壳 / 本机不通` 三类，必须换通道穿透（WebFetch / 完整浏览器 UA）：

| 穿透后看到 | 判定 |
|---|---|
| 正文含该导师姓名/职称/院系 | 有效，保留 |
| "The page does not exist" / "Page not found" | **真失效**——替换或删除；CityU 场景还要走离任检测（见 `school-registry-hk.md`） |
| 仍是空壳 | 记「无法验证」，提示用户在浏览器抽查；**不要**当作已通过 |

**通过标准**：抽检链接里没有「能打开但已跳到别的页面」和「不含本人姓名」的未处置项。

## 验收③ 跑一次真实任务，记录硬门命中情况

这条**无法脚本化**，但它才是真正的验收：只有真跑一遍，才知道哪些规则读了、哪些规则被漏过。

**怎么记录**：开工时就把下面这张表建好，边做边填。写到 `data/acceptance-log.md`（append-only，人工维护，不是机器读的索引）。

```markdown
## 验收记录 YYYY-MM-DD ｜ 学生：XXX ｜ 表：<datasheetId>

| 硬门 | 本轮是否触发 | 结果 | 备注 |
|---|---|---|---|
| 搜索 Step 0 学生身份确认 | 是 | 通过 | |
| 项目底座（课程总目录 + 官方博导名单） | 是 | 通过 | 漏了 X 校，补后通过 |
| 硬门 A 主页类型过滤 | 是 | 通过 | |
| 硬门 B 研究方向硬排除 | 否 | — | 本批次方向不涉及 |
| 硬门 C 方向核心度 | 是 | 通过 | |
| 硬门 D 三座闸门（Doability） | 是 | **漏过闸门三** | 见下 |
| 写前重新 GET | 是 | 通过 | |
| 小批次 audit（每 10 条） | 是 | 通过 | 共 spawn 2 次 |
| audit-all.py 十一项 | 是 | 退出码 1 → 修正后 0 | 首轮 3 条 FAIL |
| 验收① 证据链 | 是 | 5 条抽检，2 条改写 | |
| 验收② 链接抽检 | 是 | 5 条全过 | |

### 本轮漏过的硬门与处置
- **闸门三（学位学科对口）漏过**：`博士申请信息` 出现了 3 个不同项目的 URL，
  其中 1 个项目的学位学科不是学生目标学科。**根因**：交付前没做「按 URL 去重后逐个读学科归属」。
  **处置**：删除 4 条；本表已在 `review-phase.md` §2.4 有对应步骤，本轮未执行。
- （其余无）

### 需要补进技能的规则
- 「`博士申请信息` 去重后 URL 数 > 2 时，必须逐个报告学位学科」——已直接写进
  `review-phase.md` §2.4（原本就有，属本轮没读，不是规则缺失）
```

**通过标准**：表填完整；每一条「漏过」都写清根因，并明确是「规则缺失」还是「规则没读」。
**前者**要补规则；**后者**说明规则的可见性还不够，要往更靠前的层挪（常驻 → 必读 → 阶段手册入口），
而不是再写一遍同一条规则。

## 三条验收之间的关系

```
机械部分（脚本）              人工部分（必须做）              真正的验收
─────────────────────────────────────────────────────────────────────────
第 4 项 links      →  ② 链接抽检的候选清单   →  穿透判定 + 处置
第 11 项 evidence  →  ① 证据链的候选清单     →  回原页读原句 + 处置
（无）              →  （无）                →  ③ 真跑任务 + 记录漏过哪些硬门
```

**只跑脚本不算验收。** 脚本能证明「机械项一致」，不能证明「该不该留」和「规则有没有被读」。
